# GitOps Architecture with Argo CD

This directory contains the Argo CD AppProjects, the environment bootstrap
Applications, and the ApplicationSets that generate every component
Application for the SAIL-with-ARO platform.

## Architecture Overview

An environment bootstrap installs the AppProjects and a single root
Application. That root Application creates two ApplicationSets, which discover
component payload overlays and generate one Application per component.

```text
Environment bootstrap
└── Root Application (cluster-bootstrap)
    ├── cluster-config ApplicationSet
    │   └── banners Application
    │       └── gitops/02-cluster-config/banners/overlays/<environment>
    └── cluster-services ApplicationSet
        └── external-secrets Application
            └── gitops/03-cluster-services/external-secrets/overlays/<environment>
```

There are no intermediate `cluster-config` or `cluster-services` Applications.
Those names belong to the ApplicationSets and the AppProjects.

### 1. Bootstrap Layer (`00-cluster-bootstrap/`)

Environment-specific `prod` and `non-prod` Kustomizations. Each applies the
three AppProjects and one root Application whose source is the matching
ApplicationSet overlay. This is the only layer applied by hand.

### 2. Project Layer (`01-projects/`)

Three AppProjects that define the policy boundaries:

- `cluster-bootstrap`: the root Application and the ApplicationSets.
- `cluster-config`: Applications generated by the `cluster-config` ApplicationSet.
- `cluster-services`: Applications generated by the `cluster-services` ApplicationSet.

### 3. ApplicationSet Layer (`02-applicationsets/`)

`base/` holds the two ApplicationSets. Every common Application field —
repository URL, target revision, destination cluster, AppProject, automated
sync with prune and self-heal, and the standard labels — is defined once in the
ApplicationSet template.

`overlays/prod/` and `overlays/non-prod/` patch exactly two things:

1. `/spec/generators/0/git/files/0/path` — the descriptor discovery glob.
2. `/spec/template/metadata/labels/environment` — the environment label.

These are the only Kustomize overlays in the Argo CD composition layer. They
select the environment once per category rather than once per component.

## The `appset-config.yaml` descriptor

A component environment overlay opts into deployment by containing a file named
`appset-config.yaml`. In the normal case it has a single field:

```yaml
# gitops/02-cluster-config/banners/overlays/prod/appset-config.yaml
destinationNamespace: openshift-gitops
```

Kustomize ignores the file because it is not listed as a resource, and it never
appears in rendered payload output. The ApplicationSet Git files generator
parses it and supplies the descriptor's own location as template parameters:

| Value | Derived from | Example |
| --- | --- | --- |
| Application source path | `{{.path.path}}` | `gitops/02-cluster-config/banners/overlays/prod` |
| Application name | `{{index .path.segments 2}}` | `banners` |

Because the discovery glob pins every descriptor to
`gitops/<category>/<component>/overlays/<environment>/`, path segment 2 is
always the component directory. Neither the path nor the name is typed a second
time, so neither can drift from the repository tree.

To name an Application something other than its directory, set `name`
explicitly and it wins:

```yaml
name: console-banners
destinationNamespace: openshift-gitops
```

The descriptor deliberately carries no repository URL, target revision,
project, source path, sync policy, or destination server. Those are controlled
centrally by the ApplicationSet template.

Creating a directory does not deploy it. Only a descriptor does.

## Deployment Flow

1. Install OpenShift GitOps.
2. Apply the environment bootstrap.
3. The root Application creates the `cluster-config` and `cluster-services`
   ApplicationSets.
4. Each ApplicationSet finds the `appset-config.yaml` files for the selected
   environment.
5. Each descriptor generates an Application pointing directly at its containing
   payload overlay.

## Adding a component

```text
1. Create the component's base and/or environment overlay.
2. Ensure the environment overlay builds successfully.
3. Add appset-config.yaml with destinationNamespace.
4. Commit the overlay and descriptor.
```

The discovery globs use a single-level `*`, so a component's entrypoint overlay
must live at `gitops/02-cluster-config/<component>/overlays/<environment>/` or
`gitops/03-cluster-services/<service>/overlays/<environment>/`. Nested
directories below that are internal to the component and are not discovered
independently. That fixed depth is also what makes the derived Application name
reliable.

Removing a descriptor removes the generated Application from desired state.
Treat descriptor removal as an intentional undeployment: depending on
Application finalizers it can also remove the managed resources.

## Service bundles

An operator and the instance it configures are modelled as one service
Application, not two. Argo CD sync-wave annotations do not order independently
reconciled Applications generated by an ApplicationSet, but they do order
resources inside a single Application.

External Secrets follows this pattern. Its bundle Kustomization at
`gitops/03-cluster-services/external-secrets/overlays/<environment>/` currently
references only `operator/base`; the instance is added to that same
Kustomization once its Azure configuration is available. See
[the External Secrets README](../03-cluster-services/external-secrets/README.md)
for the intended resource ordering.

ApplicationSet Progressive Sync (`RollingSync`) is intentionally not used. It
requires explicit enablement and is a Technology Preview capability in
OpenShift GitOps 1.21, and the service-bundle design does not need it.

## Directory Structure

```text
01-argocd/
├── 00-cluster-bootstrap/           # Applied by hand, once per cluster
│   ├── prod/
│   │   ├── bootstrap-application.yaml
│   │   └── kustomization.yaml
│   └── non-prod/
│       ├── bootstrap-application.yaml
│       └── kustomization.yaml
├── 01-projects/                    # AppProject policy boundaries
│   ├── cluster-bootstrap-project.yaml
│   ├── cluster-config-project.yaml
│   ├── cluster-services-project.yaml
│   └── kustomization.yaml
└── 02-applicationsets/
    ├── base/
    │   ├── cluster-config-appset.yaml
    │   ├── cluster-services-appset.yaml
    │   └── kustomization.yaml
    └── overlays/                   # Selects the discovery environment
        ├── prod/
        │   └── kustomization.yaml
        └── non-prod/
            └── kustomization.yaml
```
