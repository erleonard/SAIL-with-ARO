# Red Hat External Secrets Operator

The External Secrets operator requires customer/environment specific configuration.

## Layout

This service is deployed as a single bundle Application, generated by the
`cluster-services` ApplicationSet from the descriptor in
`overlays/<environment>/appset-config.yaml`.

```text
external-secrets/
├── operator/base/                  # Namespace, OperatorGroup, Subscription
├── instance/
│   ├── base/                       # Namespace, ExternalSecretsConfig, ClusterSecretStore
│   └── overlays/<environment>/     # Vault URL and workload identity client ID
└── overlays/<environment>/         # Bundle entrypoint + appset-config.yaml
```

The operator and its instance belong to one Application on purpose. Argo CD
sync waves order resources within an Application, but they do not order
separate Applications generated by an ApplicationSet, so keeping the pair
together is what makes the install sequence expressible.

## Enabling the instance

The bundle currently deploys only the operator. The instance is left out
because it needs an Azure Key Vault and workload identity that do not exist
yet. Its absence from `overlays/<environment>/kustomization.yaml` is the
control — there is no feature flag.

Please review and update the following files first:
* `instance/overlays/<environment>/externalsecrets-sa.yaml` — workload identity client ID
* `instance/overlays/<environment>/kustomization.yaml` — Key Vault URL patch

Then add the instance to the bundle:

```yaml
resources:
  - ../../operator/base
  - ../../instance/overlays/non-prod
```

### Intended resource ordering

OLM installs the operator asynchronously, so the instance resources must wait
for CRDs that do not exist when the Application first syncs. Order them inside
the bundle with `argocd.argoproj.io/sync-wave` annotations:

| Wave | Resources | Purpose |
| ---: | --- | --- |
| `-30` | Namespace, OperatorGroup, Subscription | Request OLM operator installation |
| `-20` | Sync hook Job | Wait for the `ExternalSecretsConfig` CRD |
| `-10` | Instance namespace, ServiceAccount, `ExternalSecretsConfig` | Configure the operator and request the operand |
| `0` | Sync hook Job | Wait for External Secrets operand CRDs |
| `10` | `ClusterSecretStore` and dependent resources | Configure the ready operand |

The custom resources should also carry
`argocd.argoproj.io/sync-options: SkipDryRunOnMissingResource=true`, because
their CRDs are created asynchronously by OLM and operator reconciliation.

## Azure Workload Identity

This configuration relies on [Azure Workload Identity](https://learn.microsoft.com/en-us/entra/workload-id/workload-identities-overview).  Work with your Azure cloud team to configure workload identity.  An example of the `az` cli commands to configure this is bellow.

```
export OIDC_ISSUER=$(az aro show \
  --name <aro-cluster-name> \
  --resource-group <aro-resource-group> \
  --query "clusterProfile.oidcIssuer" -o tsv)

az identity create \
  --name <managed-identity-name> \
  --resource-group <resource-group> \
  --location <location>

# Fetch Principal ID of the Managed Identity
export IDENTITY_PRINCIPAL_ID=$(az identity show \
  --name <managed-identity-name> \
  --resource-group <resource-group> \
  --query principalId -o tsv)

# Fetch Key Vault Scope ID
export KEYVAULT_ID=$(az keyvault show \
  --name <keyvault-name> \
  --resource-group <resource-group> \
  --query id -o tsv)

# Assign Key Vault Secrets User Role
az role assignment create \
  --assignee-object-id $IDENTITY_PRINCIPAL_ID \
  --assignee-principal-type ServicePrincipal \
  --role "Key Vault Secrets User" \
  --scope $KEYVAULT_ID

az identity federated-credential create \
  --name <federated-cred-name> \
  --identity-name <managed-identity-name> \
  --resource-group <resource-group> \
  --issuer "$OIDC_ISSUER" \
  --subject "system:serviceaccount:<eso-namespace>:<eso-service-account-name>" \
  --audience "api://AzureADTokenExchange"

az identity show \
  --name <managed-identity-name> \
  --resource-group <resource-group> \
  --query clientId -o tsv
```
